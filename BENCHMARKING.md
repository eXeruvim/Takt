# Измерения Oxide

Производительность измеряется в отдельном профиле `profiling`: это release-сборка
с символами для профилировщика. Debug-запуск через `cargo run` не подходит для
сравнения CPU, памяти или задержек.

## Быстрый сценарный замер

1. Соберите неизменённый commit:

   ```powershell
   cargo build --profile profiling --locked --offline
   ```

   В executable встраиваются commit, версия пакета и признак чистоты
   отслеживаемых исходников. Перед настоящим замером скрипт вызывает
   `oxide.exe --build-info` и откажется подписывать старую либо собранную из
   изменённого дерева программу текущим commit. После каждого benchmark-коммита
   профильную сборку поэтому нужно выполнить заново. `-AllowUnverifiedBuild`
   предназначен только для чернового одиночного прогона; в серии ему соответствует
   `-AllowDirty`, а результат не считается кандидатом в baseline.

2. Запустите один сценарий, например двухминутное воспроизведение аудио:

   ```powershell
   .\scripts\measure-oxide.ps1 -Scenario audio -DurationSeconds 120
   ```

   Для видео режим декодирования и фактический backend указываются явно, чтобы
   результаты разных путей вывода нельзя было случайно смешать:

   ```powershell
   .\scripts\measure-oxide.ps1 `
     -Scenario video-1080p `
     -DecoderMode hardware-auto-copy `
     -RendererBackend integrated-opengl `
     -WindowMode maximized `
     -Theme dark `
     -MediaPath C:\media\sample-1080p.mp4
   ```

   Основные режимы декодера: `software`, `hardware-auto-copy`; backend:
   `integrated-opengl`, `native-hwnd-fallback`. Для video-сценариев эти два
   параметра обязательны. `hardware-auto-copy` означает продуктовую цепочку
   Oxide: NVDEC copy-back на совместимой NVIDIA либо безопасный кросс-вендорный
   copy-back fallback. Фактические значения после запуска видео показаны в
   Inspector → «Настройки воспроизведения» в строке аппаратного декодирования:
   `OpenGL` соответствует `integrated-opengl`, `HWND` — `native-hwnd-fallback`.
   `MediaPath` не сохраняется: в результат попадают только
   расширение, размер и SHA-256 файла. Произвольные локальные пояснения можно
   добавить через `-Notes`.

   Для стандартной профильной сборки скрипт при необходимости копирует корневой
   `mpv-2.dll` рядом с executable под ожидаемым загрузчиком именем
   `libmpv-2.dll`. Нестандартный executable должен поставляться со своей DLL.

3. Скрипт откроет Oxide. Настройте указанный сценарий, дождитесь стабилизации и
   нажмите Enter в терминале. Во время записи не выполняйте посторонних действий;
   оставшееся время отображается индикатором в терминале.

Доступные сценарии: `idle`, `audio`, `video-1080p`, `video-4k`,
`large-playlist`, `large-artwork`. Аппаратное декодирование и тему фиксируйте
в имени или заметке к результату и не меняйте внутри одного замера.

Сырые образцы сохраняются в `benchmark-results/*.csv`, сводка — в JSON рядом.
Каталог исключён из Git: он содержит характеристики конкретного компьютера.
JSON фиксирует commit, чистоту рабочего дерева, версии Rust/Cargo, хеши
`Cargo.lock`, executable и `mpv-2.dll`, ОС, CPU, GPU, RAM, накопители, активный
план питания и источник питания. После настройки сценария снимаются DPI,
физический и логический размер клиентской области окна. Отдельно сохраняются
заявленные режим декодера, backend, тема и режим окна. CPU нормирован к суммарной
мощности всех логических процессоров, то есть близок к представлению Диспетчера
задач. Windows-счётчики `GPU Process Memory` снимаются тем же временным рядом:
в CSV и JSON отдельно попадают p50/p95/p99/пик dedicated и shared GPU memory,
а также local/non-local и total committed. Пары dedicated/shared и
local/non-local являются двумя классификациями одних GPU-аллокаций — складывать
их между собой нельзя. Если драйвер не публикует счётчики для PID, сводка явно
содержит `available: false`, а не подставляет ноль.

Самопроверка без запуска окна:

```powershell
.\scripts\measure-oxide.ps1 -Scenario idle -ValidateOnly
```

## Предрелизный smoke-тест

После сборки чистого commit проверьте, что profiling-приложение действительно
создаёт главное окно, остаётся запущенным и принимает штатный запрос закрытия:

```powershell
.\scripts\smoke-oxide.ps1
```

Скрипт работает только со своим PID, не использует `Stop-Process` и при отказе
закрытия оставляет окно пользователю. Для стандартной profiling-сборки он также
сверяет встроенные commit и признак чистого дерева.

Короткое видео можно передать этому же тесту. Пока окно открыто, вручную
убедитесь, что появились изображение и звук, началось воспроизведение и движется
таймлайн:

```powershell
.\scripts\smoke-oxide.ps1 -MediaPath "C:\Медиа\короткое видео.mp4" -VisibleSeconds 8
```

Скрипт проверяет жизненный цикл процесса, но не пытается программно оценивать
содержимое кадра или звук. Проверка путей без GUI:

```powershell
.\scripts\smoke-oxide.ps1 -ValidateOnly
```

## Сводка повторных прогонов

Полную серию из пяти запусков выполняет один сценарный скрипт:

```powershell
.\scripts\run-benchmark-series.ps1 `
  -Scenario idle `
  -Runs 5 `
  -DurationSeconds 120
```

Для `idle` запуск, прогрев, замер и обычное закрытие каждого созданного экземпляра
Oxide выполняются автоматически. В аудио-, видео- и playlist-сценариях перед
каждым прогоном остаётся осознанный ручной шаг: откройте нужный файл, проверьте
фактический decoder/backend и нажмите Enter. Скрипт никогда не завершает Oxide
принудительно: если обычное закрытие не сработало за 10 секунд, серия
останавливается, а окно оставляется пользователю.

После последнего прогона серия агрегируется автоматически. Отдельно собрать уже
существующие результаты можно командой:

```powershell
.\scripts\summarize-benchmark-results.ps1 -Scenario idle
```

Скрипт не объединяет результаты только по похожему имени. В одну группу попадают
лишь совпадающие commit и хеши сборки/runtime, длительность и интервал, медиа,
decoder/backend, тема, режим и размер окна, DPI, оборудование, драйверы и питание.
Незавершённые прогоны и dirty working tree по умолчанию исключаются. Для черновой
проверки механики серии можно явно передать `-AllowDirty`, а агрегатору —
`-IncludeDirty`, но такой отчёт получает тип `pilot-aggregate`, а не
`baseline-candidate`. Неотслеживаемые файлы не меняют статус сборки и не мешают
baseline; изменения отслеживаемых файлов учитываются всегда.

Итоговый `aggregate-*.json` хранит исходные значения и min/p50/p95/max между
прогонами для CPU, working/private memory, dedicated/shared GPU memory, handles
и threads. Старые schema 2 результаты без GPU-счётчиков остаются читаемыми:
соответствующие агрегаты в них отсутствуют. Самопроверка:

```powershell
.\scripts\summarize-benchmark-results.ps1 -Scenario idle -ValidateOnly
.\scripts\run-benchmark-series.ps1 -Scenario idle -ValidateOnly
```

## Корпус медиа

Схема и целевая матрица описаны в
[`benchmark-corpus/README.md`](benchmark-corpus/README.md). Локальные образцы и
манифест намеренно исключены из Git, пока для каждого файла не подтверждены
источник и право распространения. Размеры, SHA-256, уникальность идентификаторов
и безопасные относительные пути проверяются командой:

```powershell
.\scripts\verify-benchmark-corpus.ps1
```

Перед финальным baseline используйте `-RequireReleaseCoverage`: проверка также
потребует все обязательные разрешения, fps, кодеки и особые признаки корпуса.

### Fixture большой очереди

Для проверки масштабирования создайте отдельные наборы на 100, 1 000 и 10 000
имён короткого беззвучного WAV. Последний набор одновременно проверяет продуктовый
лимит очереди в 5 000 элементов. Из-за лимита NTFS генератор использует несколько
физических WAV-шардов, не более 800 ссылок на каждый; остальные имена — hard links.
По умолчанию 10 000 имён занимают примерно 33 МиБ вместо десятков гигабайт копий.

```powershell
.\scripts\new-large-playlist-fixture.ps1 -FileCount 100
.\scripts\new-large-playlist-fixture.ps1 -FileCount 1000
.\scripts\new-large-playlist-fixture.ps1 -FileCount 10000

.\scripts\run-benchmark-series.ps1 `
  -Scenario large-playlist `
  -DurationSeconds 60 `
  -WorkloadManifest .\.tmp\benchmarks\large-playlist-<timestamp>\fixture.json
```

Во время каждого запуска откройте папку, в которой лежит указанный `fixture.json`,
откройте очередь и только затем нажмите Enter. Для набора 10 000 убедитесь в
уведомлении о 5 000 пропущенных файлах. Измеритель сверяет число WAV с паспортом;
SHA-256 паспорта входит в сигнатуру и не позволяет объединить разные размеры.
Fixture создаётся в уникальной папке `.tmp/benchmarks` и не удаляется
автоматически. Удалить её после проверки можно через Проводник.

### Фазы загрузки очереди

Общий CPU приложения не показывает, что именно замедляет большую очередь. Поэтому
отдельный profiling-инструмент вызывает те же функции производственного модуля и
измеряет обход каталога с применением лимитов, natural sort, создание ограниченных
UTF-8-подписей, преобразование в `SharedString`, создание `VecModel` и полное
время. Создание модели измеряется без окна; присвоение модели, layout и отрисовку
открытой панели Slint нужно измерять сценарно в приложении. IPC переносит владение
готовым `Vec<String>` и отдельно учитывается только при появлении подтверждённой
задержки очереди событий.

Соберите инструмент из чистого commit и передайте паспорт нужного fixture:

```powershell
cargo build `
  --profile profiling `
  --features benchmark-tools `
  --bin oxide-playlist-bench `
  --locked `
  --offline

.\scripts\measure-playlist-phases.ps1 `
  -Manifest .\.tmp\benchmarks\large-playlist-<timestamp>\fixture.json `
  -Iterations 25 `
  -WarmupIterations 3
```

Отчёт `benchmark-results/playlist-phases-*.json` не содержит локальный путь. В нём
сохраняются build provenance, SHA-256 паспорта, число сохранённых/отброшенных
элементов и все сырые значения вместе с min/p50/p95/max. Скрипт не принимает
устаревшую или dirty-сборку без явного `-AllowDirty`; такой запуск годится только
для проверки механики.

При интерпретации `directory_scan` учитывайте стоимость проверки типа каждого
элемента. Обычные файлы должны использовать уже полученный `DirEntry::file_type`;
повторный `Path::is_file` для каждого имени на Windows создаёт отдельный запрос
метаданных. Следование ссылке и fallback при ошибке остаются отдельными редкими
ветвями, поэтому их нельзя механически удалить ради цифры benchmark.

## Правила сравнения

- Сравнивайте только одинаковые файлы, настройки, питание, размер окна и backend.
- Не используйте `not-recorded` для итогового video baseline: decoder и renderer
  там обязательны. Для idle, audio и playlist `decoder_mode: not-recorded`
  означает «не применимо» и допустим, если остальные параметры зафиксированы.
- Выполняйте минимум пять прогретых запусков каждого варианта; храните все выбросы.
- Cold start процесса и холодный файловый кэш — разные эксперименты.
- Working set может меняться из-за системного кэша. Для утечки важнее устойчивый
  рост private bytes, handles или threads после одинаковых завершённых циклов.
- Итоговый baseline 1.0 требует также frame-time и GPU engine/time из внешнего
  профилировщика. Встроенный замер покрывает объём GPU-памяти процесса, но не
  раскрывает назначение отдельных текстур и не подменяет RenderDoc/WPA.

## Предрелизные бюджеты 1.0

Ниже зафиксированы локальные пороги для контрольной машины Ryzen 5 5600X,
RTX 4070 SUPER, Windows 11 build 26200, 2560×1440/165 Гц и профиля высокой
производительности. Это regression gate для сопоставимых прогонов, а не обещание
одинаковых абсолютных значений на любом компьютере. Новый baseline принимается
только серией не менее пяти запусков; превышение порога требует профиля либо
обоснованного пересмотра бюджета, а не простого увеличения числа.

| Сценарий | CPU | Working Set p95 | Private Bytes p95 | GPU dedicated/shared p95 | Дополнительный gate |
| --- | --- | ---: | ---: | ---: | --- |
| Idle | p95 ≤ 0,5%, p99 ≤ 1,0% | ≤ 100 МиБ | ≤ 150 МиБ | ≤ 50/20 МиБ | нет постоянной перерисовки; рост второй половины ≤ 1 МиБ/мин |
| Audio, видимое окно | p95 ≤ 1,5%, p99 ≤ 2,1% | ≤ 175 МиБ | ≤ 235 МиБ | ≤ 80/30 МиБ | рост второй половины ≤ 1 МиБ/мин; handles ≤ 1200, threads ≤ 45 |
| 1080p/29,97, software, integrated OpenGL | p95 ≤ 2,1%, p99 ≤ 3,2% | ≤ 260 МиБ | ≤ 500 МиБ | ≤ 250/110 МиБ | 0 VO/decoder drops и delayed; interval p95/p99 ≤ 37/43 мс; mpv render p99 ≤ 37 мс |

Порог audio намеренно включает холодный переход первой серии alpha.38:
161,36 МиБ Working Set, 221,29 МиБ Private Bytes и 1147 handles с последующим
освобождением 5,12/25,48 МиБ и 325 handles. Остальные четыре процесса дали
110,06–110,54 МиБ Working Set p95, 168,40–171,02 МиБ Private Bytes p95 и
443–445 handles. Выброс хранится в исходных данных и не исключается; отдельный
cold-start/file-picker сценарий нужен, прежде чем приписывать его конкретному
компоненту Windows или Oxide.

Для pause обязательны 0 постоянных кадров и CPU, неотличимый от idle; для
minimized — 0 кадров Slint и не более 0,25% общей CPU-мощности на этой машине.
Аппаратное декодирование пока не входит в обязательный release baseline. Старый
прогон `d3d11va-copy` увеличивал CPU/RAM/VRAM и содержал визуальные артефакты;
после исправления изоляции OpenGL-состояния и введения кросс-вендорной цепочки
нужен новый A/B `software` → `hardware-auto-copy`. До него режим остаётся
выключенным по умолчанию. 4K/60, другие кодеки, energy и end-to-end presentation
имеют отдельные паспорта и не должны молча оцениваться по таблице 1080p.

## Системная трасса CPU, GPU и пробуждений

Обычная выборка раз в 250 мс не показывает короткие функции, context switches и
причину пробуждения потока. Для этого используется встроенный Windows Performance
Recorder. Сначала соберите profiling-версию из чистого commit, затем запишите
отдельную системную ETL-трассу:

```powershell
.\scripts\capture-oxide-wpr.ps1 -Scenario idle -Profile CPU -DurationSeconds 30
.\scripts\capture-oxide-wpr.ps1 -Scenario video-1080p -Profile GPU -DurationSeconds 30 -MediaPath C:\media\sample.mp4 -DecoderMode hardware-auto-copy -RendererBackend integrated-opengl -WindowMode windowed -Theme dark
```

Для media-сценария скрипт откроет Oxide и подождёт подтверждения после настройки
воспроизведения. `idle` выполняется автоматически. Доступны штатные профили `CPU`,
`GPU`, `Power`, `GeneralProfile`, `Heap`, `Video`, `ResidentSet`, `ReferenceSet`
и `VirtualAllocation`. Один прогон отвечает на один вопрос; не объединяйте
несколько тяжёлых профилей и не сравнивайте разные режимы.

Для `video-1080p` и `video-4k` режим декодирования и renderer обязательны: это
не позволяет случайно сопоставить software decode с аппаратным или целевой
композитный OpenGL-путь с диагностическим HWND fallback. `-WindowMode`, `-Theme`
и необязательный `-Notes` также попадают в JSON-паспорт. Указывайте фактически
выбранное в интерфейсе состояние, а не желаемую конфигурацию.

Скрипт отказывается работать с dirty/устаревшей сборкой и не вмешивается, если WPR
уже занят другой записью. При ошибке он отменяет только начатую им сессию и
запрашивает обычное закрытие созданного окна — принудительное завершение не
используется. Трасса и JSON-паспорт сохраняются в `benchmark-results/wpr`.

ETL является системной трассой: она содержит имена процессов и может содержать
локальные пути. Каталог исключён из Git; не публикуйте файл без проверки.
Для просмотра стеков, CPU Usage, Context Switches и GPU engines нужен
Windows Performance Analyzer из Windows Performance Toolkit. Наличие WPR без WPA
позволяет записать данные, но не даёт честно определить горячие функции.
Dedicated/shared GPU memory измеряет `measure-oxide.ps1` напрямую; штатный WPA
Exporter может не выгрузить VidMm-таблицу даже из GPU ETL, поэтому отсутствие
такого CSV не интерпретируется как нулевой расход VRAM.
Системные профили обычно требуют PowerShell, запущенный от имени администратора,
либо права Windows «Profile system performance». При отказе `0xc5585011` скрипт
не создаёт трассу, закрывает запущенный Oxide и не оставляет активную WPR-сессию.

Самопроверка путей и доступности профиля без запуска приложения и записи ETL:

```powershell
.\scripts\capture-oxide-wpr.ps1 -Scenario idle -Profile CPU -ValidateOnly
```

После записи CPU-трассы экспортировать срезы Oxide по модулю, функции, sampled
потоку и точным context switches можно без ручной настройки таблиц WPA. Скрипт
по умолчанию выбирает самый свежий паспорт в `benchmark-results/wpr`, берёт из
него точный PID процесса и сохраняет производные CSV рядом в игнорируемом
каталоге `analysis`. Там же создаётся `oxide-cpu-summary.json` с агрегатами по
модулям, функциям, потокам и источникам пробуждения самого активного потока:

```powershell
.\scripts\export-oxide-wpa.ps1
```

`-Symbols` включает разрешение имён только через PDB текущей сборки из
`target/profiling`; публичные symbol servers скрипт намеренно не подключает.
Без флага используются лишь уже созданные symcache. Исходная ETL не изменяется.

### GPU engines и парное сравнение декодеров

Для профиля `GPU` используется отдельный экспортёр. Он берёт точный PID и режимы
из паспорта, создаёт две таблицы — только Oxide и системную — и группирует задачи
по типу GPU-движка:

```powershell
.\scripts\export-oxide-gpu.ps1
```

`one_engine_timeline_percent` — сумма GPU time, делённая на длительность трассы
одного движка. Это не процент всей видеокарты: параллельные движки складывать
нельзя. Отсутствие строки `Video Decode` в одиночной трассе не доказывает software
fallback, поскольку драйвер может атрибутировать работу иначе.

Для проверки аппаратного пути снимите одним commit, бинарником и медиа два прогона
`software` и `hardware-auto-copy`, экспортируйте оба и сравните их:

```powershell
.\scripts\compare-oxide-gpu.ps1 -SoftwareSummaryPath C:\path\software\oxide-gpu-summary.json -HardwareSummaryPath C:\path\hardware\oxide-gpu-summary.json
```

Скрипт откажется сравнивать разные SHA-256 бинарника, mpv или медиа, commit,
renderer, режим окна, тему и сценарий. Сравнение GPU не заменяет отдельные CPU,
frame pacing, energy и dedicated/shared GPU-memory измерения.

Лёгкие замеры CPU и памяти из `measure-oxide.ps1` сравниваются отдельно. Передайте
парные результаты `software` и `hardware-auto-copy`; анализатор также проверит commit,
SHA-256, медиа, длительность, окно, тему, оборудование и питание:

```powershell
.\scripts\compare-oxide-decoder.ps1 -SoftwareResultPath .\benchmark-results\software.json -HardwareResultPath .\benchmark-results\hardware.json
```

Выходной `oxide-decoder-comparison.json` содержит абсолютные и относительные
дельты CPU, Working Set, Private Bytes, dedicated/shared GPU memory, трендов
памяти, handles и threads. Для старой пары без GPU-счётчиков эти поля помечаются
как недоступные, поэтому прежние результаты остаются совместимыми. Если
оба запуска содержат `playback_diagnostics`, туда же входят фактический декодер,
VO/decoder drops, delayed/mistimed, частота и A/V sync. Одна
пара годится для диагностики направления, но release-бюджет принимается только
по серии из пяти и более чистых прогонов плюс frame pacing/GPU/energy.

Для media-сценария с `-CloseAfterMeasurement` лёгкий измеритель также запрашивает
у встроенного mpv финальные счётчики текущего файла и добавляет в JSON поле
`playback_diagnostics`: кадры, отброшенные VO и декодером, mistimed/delayed,
частоты, vsync и A/V sync. В benchmark-режиме дополнительно измеряются интервалы
вызовов встроенного OpenGL renderer и длительность `mpv_render_context_render`
с p50/p95/p99. В `render_timing.scene_by_surface` отдельно записаны `empty`,
`video` и `audio`: интервал кадров, участок Slint `BeforeRendering` →
`AfterRendering` и его остаток после вычитания вложенного `mpv_render`. Последний
показатель включает отрисовку Slint и служебный notifier-код, но не является
чистым временем layout. Это frame pacing внутри Oxide/Slint, а не фактическая
задержка показа DWM, ожидание GPU или дисплея; внешний PresentMon/WPA по-прежнему
нужен для end-to-end.
Временный диагностический файл удаляется после
слияния со сводкой; обычный запуск Oxide его не создаёт. Счётчики охватывают
текущий файл с момента загрузки, включая ручную настройку и прогрев. Поэтому
сравнивайте только одинаковые действия и длительность. `vo-delayed-frame-count`
является эвристикой mpv, а не точным доказательством пропуска кадра; frame-time
p50/p95/p99 по этим счётчикам не вычисляется.

### Физически резидентная память

`Working Set` из быстрого измерителя полезен для тренда, но не показывает состав
страниц. Для снимка физически резидентной памяти в конце сценария запишите профиль
`ResidentSet` из PowerShell, запущенного от имени администратора:

```powershell
.\scripts\capture-oxide-wpr.ps1 -Scenario audio -Profile ResidentSet -DurationSeconds 30 -WarmupSeconds 5
.\scripts\export-oxide-memory.ps1
```

Экспортёр берёт точный PID из паспорта и создаёт четыре независимых среза:
итог по процессу, списки памяти, категории страниц и описания файлов/образов.
Итоговый `oxide-resident-memory-summary.json` не складывает уровни иерархии WPA
между собой. `Resident Set` — снимок страниц в физической памяти в конце записи;
он не равен Private Bytes/commit и сам по себе не доказывает утечку. Если рост
Private Bytes повторяется после прогрева, следующим отдельным экспериментом
используйте `VirtualAllocation`, а heap-трассу снимайте только для подтверждённого
роста и заранее выбранного процесса.

Для `VirtualAllocation`, `ReferenceSet` и `Heap` сборщик запускает WPR до Oxide,
чтобы не потерять стартовые выделения. Поэтому их ETL включает также время ручной
настройки сценария и прогрев; паспорт отдельно хранит начало всей записи и начало
фиксированного окна измерения. CPU/GPU и Resident Set по-прежнему записываются
после настройки сценария: первым нужен чистый steady-state интервал, второй всё
равно является снимком на момент остановки.

Паспорт отделяет время запроса остановки от долгой записи ETL на диск:
`actual_trace_duration_seconds` заканчивается перед `wpr -stop`, а
`export_flush_seconds` показывает длительность финализации файла. Это не позволяет
случайно принять время экспорта за дополнительные секунды измеряемого сценария.

### Виртуальные выделения и private commit

Чтобы разложить стартовую private-память по стекам, запишите отдельную трассу и
экспортируйте её через WPA:

```powershell
.\scripts\capture-oxide-wpr.ps1 -Scenario audio -Profile VirtualAllocation -DurationSeconds 30 -WarmupSeconds 5
.\scripts\export-oxide-virtual-allocation.ps1 -Symbols
```

Экспортёр создаёт `oxide-virtual-allocation-summary.json`, четыре исходных CSV и
производный WPA-профиль. `Outstanding Committed` — объём виртуальной памяти, для
которой система обязалась предоставить RAM или pagefile; это не то же самое, что
физически резидентный Working Set. `Outstanding Reserved` лишь занимает диапазоны
виртуального адресного пространства. Поэтому десятки гигабайт reserved нельзя
называть потреблением ОЗУ.

Строки Stack в WPA включающие: дочерний вызов уже входит в значение родителя.
Сводка отдельно хранит непересекающиеся ветви на глубине 3 и ориентиры максимального
включающего объёма для функций/модулей. Ориентиры нельзя складывать между собой;
они нужны, чтобы найти путь крупного выделения и затем поставить отдельный A/B
эксперимент. Полное дерево остаётся в CSV. `-Symbols` разрешает имена Oxide через
локальную PDB; отсутствие PDB системных DLL не мешает итогам по байтам.
